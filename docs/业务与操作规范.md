# 业务与操作规范

> 适用项目：上云 API 无人机巡检系统私有化部署。
>
> 这份文档回答四个问题：系统要做什么、谁可以操作、操作后应该发生什么、目前还缺什么。它是后续开发、测试和验收的共同依据。

---

## 一、当前项目真实状态

目前已完成的是**可运行的模拟原型**：有指挥中心、任务管理、事件管理和 Spring Boot 后端；模拟设备状态、任务进度与告警会通过 WebSocket 实时推送到网页，告警可填写处理结果并确认。

目前还没有接入真实无人机、机库、气象站、视频流或大疆上云 API，也没有 MySQL 持久化。因此，当前网页中的设备状态、航线、任务和告警仍是模拟数据，不能用于真实飞行操作。

---

## 二、优先级与开发顺序

| 优先级 | 范围 | 为什么先做 |
|---|---|---|
| P0（第一阶段） | 实时监控、在线运维、设备状态与告警、设备控制、上云 API 接入 | 这是系统能“看到设备、知道是否安全、再安全地操作设备”的基础 |
| P1（第二阶段） | 航线规划、任务设定 | 有了可靠设备数据后，才能安全安排自动飞行 |
| P2（第三阶段） | 远程智能管控、成果查看 | 依赖前两阶段的数据、任务和飞行记录 |

> P0 内部也要按顺序完成：先接入数据和状态，再做告警，再做控制。不能先做控制按钮，否则网页看起来能控制，实际却没有安全判断。

---

## 三、功能需求与操作规范

### 1. 实时监控（P0）

**要解决的问题**：操作人员无需到现场，也能看到作业实况。

**系统应具备的能力**：

- 同时展示多路实时视频，例如不同无人机或不同机库摄像头。
- 可选择某一路放大查看，并显示设备名称、直播状态和当前时间。
- 视频断开时明确显示“视频连接中”或“视频已中断”，不能显示旧画面冒充实时画面。

**操作规则**：

1. 用户进入“实时监控”后选择需要查看的设备。
2. 系统先检查用户是否有查看权限，再请求视频播放地址。
3. 用户只查看视频时，不应触发飞行或设备控制。

**验收标准**：在测试设备正常推流时，网页可稳定展示至少一路实时画面；断流后 10 秒内给出明显提示。

**当前差距**：未开发。现有指挥中心只有模拟飞行地图，没有视频流。

---

### 2. 在线运维（P0）

**要解决的问题**：无需前往现场，即可了解机库、飞行器和挂载设备是否可用。

**系统应具备的能力**：

- 查看机库门、充电、网络、温度等状态。
- 查看无人机在线状态、电量、定位、飞行状态和最近上报时间。
- 查看挂载设备的连接和工作状态。
- 状态数据必须带“最后更新时间”；超过设定时间未更新时显示“数据过期”。

**操作规则**：

1. 运维人员先查看设备状态，再决定是否创建任务或执行控制。
2. 页面只显示已由后端确认的数据，不直接相信浏览器自己生成的数据。
3. 发现离线、低电量或数据过期时，系统必须给出醒目提示。

**验收标准**：测试设备状态变化后，网页在 5 秒内更新；设备超过 60 秒没有状态上报时标记为异常或离线。

**当前差距**：网页已接收模拟后端的实时无人机状态；仍没有真实设备、机库状态、挂载状态和数据过期判断。

---

### 3. 设备状态检测与告警（P0）

**要解决的问题**：提前发现不适合飞行或设备异常的情况，避免冒险起飞。

**系统应具备的能力**：

- 检测无人机、机库和气象站的状态。
- 识别大雨、大风、低电量、网络中断、机库异常等情况。
- 自动创建告警，记录发生时间、设备、等级、原因和处理状态。
- 告警分为提示、一般、高、紧急四级；高和紧急告警需要在指挥中心明显展示。

**操作规则**：

1. 高或紧急天气告警存在时，系统不允许新任务起飞。
2. 已在飞行中的任务遇到高风险天气时，后端先执行预设安全策略，例如返航或就近降落；网页只负责展示状态和请求人工确认。
3. 运维人员处理告警时必须填写处理结果，保留处理人和处理时间。

**验收标准**：模拟大风或强降雨数据后，30 秒内出现告警；尝试起飞时系统明确阻止并说明原因。

**当前差距**：后端已根据模拟风速生成一条“一般”告警，网页可确认并展示处理记录；仍未接入真实气象站、多规则判断、MySQL 持久化或高风险自动阻止逻辑。

---

### 4. 设备控制（P0）

**要解决的问题**：通过网页安全地远程控制机库、无人机和挂载，不依赖现场遥控器。

**可控制范围**：

- 机库：开关舱门、充电、重启或状态刷新。
- 无人机：起飞、返航、降落、暂停任务、继续任务。
- 挂载：按设备能力进行拍照、录像、变焦或切换工作模式。

**安全操作规则（必须执行）**：

1. 只有被授权的“飞行操作员”或“管理员”可以看到控制按钮。
2. 起飞、降落、返航、开关舱门等高风险操作必须二次确认，并显示操作对象与当前状态。
3. 每次控制前，后端必须检查设备在线、电量、气象、机库状态和当前任务状态。
4. 前端不能直接向无人机发送命令，必须通过后端转发并记录。
5. 每次控制都要写入操作日志：谁在何时对哪个设备执行了什么操作，结果是否成功。
6. 控制失败时必须显示失败原因，不能只显示“已发送”。

**验收标准**：在测试环境中，已授权用户可完成一次安全检查通过的控制；未授权用户无法发起控制；所有操作可在日志中查到。

**当前差距**：未开发。当前网页没有真实控制命令、权限、二次确认、操作日志或安全检查。

---

### 5. 航线规划（P1）

**要解决的问题**：在地图上制作可复用的飞行路线。

**系统应具备的能力**：

- 在 2D 地图上绘制、编辑、保存航线；3D 地图作为后续增强项。
- 支持高空摄影、自定义航点飞行等模式。
- 为每个航点配置高度、速度、拍摄动作和挂载参数。
- 保存前检查路线是否完整、航点参数是否合理。

**操作规则**：航线必须有名称、所属区域、创建人和最后修改时间；修改已被任务使用的航线时，系统要提示可能影响后续任务。

**验收标准**：用户可创建一条至少含三个航点的路线，保存后能再次打开并编辑。

**当前差距**：未开发。前端导航中存在入口，但没有规划功能。

---

### 6. 任务设定（P1）

**要解决的问题**：让无人机按现在或未来的时间规则自动执行航线任务。

**系统应具备的能力**：

- 选择航线、执行设备、开始时间和负责人。
- 支持立即执行、指定时间执行和按天/周重复执行。
- 展示任务状态：草稿、待执行、执行中、已完成、失败、已暂停。
- 记录每一次实际执行的开始、结束、失败原因和飞行记录。

**操作规则**：创建任务不等于立即起飞。真正执行前，后端仍需要进行设备和气象安全检查。

**验收标准**：可创建一次性和重复性任务；系统能在指定时间产生待执行任务；安全检查不通过时任务不执行并留下原因。

**当前差距**：前端已有任务列表、状态筛选和详情的演示页面；没有保存、调度、时间规则或真实执行能力。

---

### 7. 远程智能管控（P2）

**要解决的问题**：根据设备状态和气象数据自动执行安全动作，减少人工盯守。

**系统应具备的能力**：

- 综合电量、风速、降雨、网络、机库和任务状态进行判断。
- 自动决定允许起飞、暂缓任务、返航或降落。
- 所有自动决定要保留原因、规则版本和执行结果，方便追溯。

**操作规则**：自动控制只能在已配置的安全规则范围内执行；管理员可以暂停自动管控，但不能绕过高风险天气限制。

**验收标准**：模拟高风险天气时，系统能阻止待起飞任务；模拟低电量时，系统能将飞行任务切换到安全返航流程。

**当前差距**：未开发。

---

### 8. 成果查看（P2）

**要解决的问题**：飞行结束后，人员能在线查看采集的照片和视频。

**系统应具备的能力**：

- 自动关联任务、飞行记录、照片、视频和采集时间。
- 支持按任务、设备、时间查看成果。
- 支持图片预览和视频播放；文件不存在或同步失败时显示明确状态。

**操作规则**：成果文件只读保存；删除或导出需要权限并保留记录。

**验收标准**：一次测试任务结束后，至少能在任务详情中查看关联的测试照片或视频记录。

**当前差距**：未开发。

---

### 9. 上云 API 与私有化通信（P0）

**要解决的问题**：把大疆设备数据可靠、安全地接入自建的私有化系统，并向网页提供实时数据。

**总体通信路径**：

```text
无人机 / 机库 / 气象站
        ↓
DJI Cloud API（MQTT、HTTPS）
        ↓
本项目后端（Spring Boot）
        ↓
MySQL（历史数据） + 实时缓存（最新状态）
        ↓
WebSocket
        ↓
Vue 网页（指挥中心、监控、告警、控制页面）
```

**协议使用规则**：

| 协议 | 在本项目中的用途 |
|---|---|
| MQTT | 接收设备持续上报的状态、任务事件、告警等实时消息 |
| HTTPS | 查询配置、下发需要请求响应确认的业务指令、调用管理接口 |
| WebSocket | 后端将最新状态、告警和任务变化实时推送给网页 |

**接入规则**：

1. 大疆密钥、数据库密码和设备凭证只能放在后端环境变量中，不能写入前端代码或提交到 Git。
2. 后端负责验证收到的消息、保存关键历史记录，并把可展示的数据推送给前端。
3. 前端通过 `/api/v1/` 获取历史数据，通过 WebSocket 接收实时变化；前端不直接保存或暴露大疆密钥。
4. 任何控制命令都要有唯一编号、超时处理和结果回执，防止重复发送或“以为成功”。
5. 通信中断、消息格式错误和认证失败都要记录到系统日志，并在运维页面可查。

**验收标准**：先使用模拟设备消息验证整条链路：后端收到一条设备状态后，网页在 5 秒内更新；之后再替换为真实 DJI Cloud API 凭证与设备。

**当前差距**：已创建 Spring Boot 工程，并完成模拟状态和模拟告警的 WebSocket 链路；仍未接入 MQTT、真实 DJI HTTPS 接口、数据库表或真实设备凭证。

## 四、第一阶段的最小交付目标

第一阶段不追求一次做完所有功能，而是先完成一条可验证的安全链路：

1. 后端启动，并可接收一条模拟设备状态。
2. 网页指挥中心不再使用固定演示数据，而是显示后端推送的在线状态、电量和更新时间。
3. 后端根据模拟风速或降雨产生一条告警，网页实时显示。
4. 网页提供“返航”演示控制按钮；后端先检查权限和安全条件，再返回成功或失败结果并写操作日志。
5. 上述流程稳定后，再使用真实 DJI Cloud API 和设备替换模拟数据。

## 五、每次开发后的记录要求

- 前端界面、视频展示和交互改动：写入 `frontend/开发日志.md`。
- 后端通信、设备接入、告警、控制和数据库改动：写入本文件的“更新记录”，同时更新 `.project-memory.md`。
- 新增或调整操作规则时：必须说明影响哪一项需求、为什么改、如何验证。
