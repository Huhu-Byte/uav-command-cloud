# DJI Dock 3 上云数据链路

最后核验：2026-07-29。依据 DJI 官方 Cloud API 的“Pilot 上云”“机场上云”“Dock 3 设备属性”和“Dock 3 设备管理”文档。

## 一、先区分两条上云链路

### 1. Pilot 上云

Pilot 上云是把 **DJI Pilot 2 遥控器** 接入第三方平台的流程：

```text
DJI Pilot 2 → 打开第三方 H5 登录页 → H5 调用 JSBridge → Pilot 2 连接 MQTT Broker
```

1. 第三方前端提供一个 Pilot 2 可访问的 H5 登录地址。
2. H5 通过 JSBridge 校验 Cloud API 的 License，并读取/校验 Pilot 本地 Token。
3. H5 向后端取得 MQTT 地址、账号和密码，再通过 JSBridge 加载 Pilot 上云模块。
4. Pilot 2 作为 MQTT Client 连接 EMQX，并把连接结果回调给 H5 页面。

这条链路服务于遥控器、人工飞行和 Pilot 侧功能；它不是 Dock 3 的实时遥测上报链路。

### 2. 机场上云（Dock 3）

机场上云借助 **DJI Pilot 2** 完成配置，但配置完成后是 **Dock 3 自己直接连接 MQTT Broker**：

```text
Pilot 2 填写 Broker 地址和账号密码
        ↓
Dock 3 ── MQTT ──> EMQX Broker <── MQTT ── 后端 ── WebSocket ──> 前端网页
```

官方机场上云时序要求如下：

1. 在 Pilot 2 中检查机场、网络和飞行器对频，并填写 MQTT 网关地址、账号和密码。
2. Dock 3 与 EMQX 建立 MQTT 连接。
3. Dock 3 在 `thing/product/{gateway_sn}/requests` 发送 `config` 请求；后端必须在 `requests_reply` 返回 App ID、App Key、App License 和 NTP 配置。
4. Dock 3 校验 License。成功后，继续通过 `requests` / `requests_reply` 查询并绑定组织。
5. Dock 3 在 `sys/product/{gateway_sn}/status` 以 `update_topo` 上报网关与子设备拓扑；后端必须在 `status_reply` 返回处理结果。
6. 正常上线后，Dock 3 持续上报属性和状态，后端订阅、解析并推送网页。

## 二、Dock 3 实时数据与应答

| Topic | 方向 | 用途 |
|---|---|---|
| `thing/product/{device_sn}/osd` | Dock 3 → 后端 | 定频属性，官方 Dock 3 文档标注为 `0.5 Hz`。 |
| `thing/product/{device_sn}/state` | Dock 3 → 后端 | 状态变化时上报。 |
| `sys/product/{gateway_sn}/status` | Dock 3 → 后端 | 设备上线、下线和拓扑更新。 |
| `sys/product/{gateway_sn}/status_reply` | 后端 → Dock 3 | 对 `update_topo` 的处理应答。 |
| `thing/product/{gateway_sn}/requests` | Dock 3 → 后端 | 配置、License、组织绑定等请求。 |
| `thing/product/{gateway_sn}/requests_reply` | 后端 → Dock 3 | 对上述请求的应答。 |

`osd`、`state` 和 `status` 是只读展示的基础；`requests_reply` 与 `status_reply` 是 Dock 3 完成上云流程所需的服务端能力，不能只订阅不应答。

## 三、Pilot 与机场 Topic 的关系

Pilot 上云与机场上云的两份官方 Topic 定义使用同一组基础 Topic 外壳：`osd`、`state`、`services`、`events`、`requests`、`status`、`property/set` 和 `drc`。它们不能因为 Topic 名相同就混为同一业务数据：

- **Pilot 上云**：`gateway_sn` 对应 Pilot 侧的网关设备，消息描述遥控器、其连接的飞行器及 Pilot 业务。
- **机场上云**：`gateway_sn` 对应 Dock 3，`status` 的 `update_topo` 会说明 Dock 与其子设备飞行器的拓扑；属性页定义的是机场、飞行器、电池、网络、舱盖等数据。

后端收到消息后，应先根据 `gateway_sn` 与 `update_topo` 识别设备类型，再选择对应的数据解析器；不能把 Pilot 的设备属性按 Dock 3 属性处理，或反过来处理。下行 `services`、`property/set`、`drc/down` 都属于设备操作入口，当前阶段不发布这些消息。

## 四、两种部署方式

### 方式 A：前端、后端和 EMQX 都部署到云服务器

```text
Pilot 2 / Dock 3 → Internet → 云端前端、后端和 EMQX
```

- Pilot 2 可访问云端 H5 登录页。
- Dock 3 通过现场网络连接云端 EMQX。
- 适合集中维护；需做好公网访问、TLS 证书、账号密码和防火墙配置。

### 方式 B：现场网线接入的本地部署

```text
Pilot 2 / Dock 3 → 现场局域网 → 现场前端、后端和 EMQX
```

- Dock 3 和部署服务器通过网线接入同一局域网。
- Pilot 2 需能访问本地 H5 页面，并在机场上云配置中填写本地 Broker 地址和账号。
- 仍然需要 EMQX；所谓“网线直连”是 Dock 3 直连局域网内的 Broker，不是绕过 Broker 直连 Spring Boot。
- 官方文档的部署示例称其为“Cloud Server”。本地局域网部署在协议上可使用 TCP/IP MQTT，但是否接受私有地址、网络路由和证书策略，必须先在测试机场按 DJI 配置流程只读验证，不能凭空假设。

## 五、当前项目完成与缺口

已完成：

- MQTT 配置和 `osd`、`state`、`status` 的订阅准备；Broker 地址、账号和密码已改为独立环境变量，不再复用 Cloud API 的 App 凭证。
- MQTT 的 Topic 配置使用 `UAV_DJI_MQTT_GATEWAY_SN`，它只代表机场网关 SN，不能填写主控 SN 或铭牌 SN。旧变量 `UAV_DJI_MQTT_DEVICE_SN` 只在当前代码中保留迁移兼容，真实连接前应替换为新变量。
- 已按官方公共报文结构实现离线应答构造：`config` 返回 App 与 NTP 参数；`airport_bind_status` 返回当前“未绑定”；`update_topo` 返回 `status_reply` 成功确认。应答会保留设备请求中的 `tid`、`bid` 与 `method`。
- 已新增“组织与设备资料”本机登记页和持久化接口：组织编号、组织名称、主控 SN、铭牌 SN、显示名称与可选机型标识会分开保存，状态固定为“待绑定”。资料登记不是 DJI 实际绑定，也不会向设备发送结果。
- 新增 `UAV_DJI_MQTT_HANDSHAKE_ENABLED=false` 第二道开关。即使未来开启 MQTT 连接，未显式开启此开关时也只会准备应答、不会发布任何 MQTT 消息。
- 新增本地 `DjiDockTelemetryParser`：只从 `osd` 报文的 `data` 对象读取经纬度、高度与电量，并校验数值范围；资料不完整或不合理时不推送快照，更不会以 `0` 代替缺失数据。当前不解析 `data.devices` 中的子设备，避免在没有拓扑确认时混用机场与飞行器属性。
- 新增本地 `DjiDockTopologyRegistry`：依据 DJI 官方 Java 示例的 `update_topo` 结构，只记录网关和 `subDevices` 的 SN、域、类型、子类型与索引，用于后续区分机场和子设备；`deviceSecret`、`nonce` 不保存、不写日志、不入库。
- 统一实时快照与网页 WebSocket 推送能力。
- 默认关闭真实连接：`UAV_DJI_MQTT_ENABLED=false`、`UAV_DJI_CLOUD_ENABLED=false`。

尚未完成：

- Pilot 上云 H5 登录页与 JSBridge 调用。
- 向 Pilot 2 提供 MQTT 登录参数的后端接口。
- `airport_organization_get`、`airport_organization_bind` 的真实查询与绑定应答；当前系统只能如实报告“未绑定”，不能因本机资料已登记就报告绑定成功。
- Dock 3 测试机场对上述通用报文与实际固件的兼容性核验。
- 按网关设备类型区分 Pilot 与 Dock 3 的完整数据解析器；当前已接收并保存最新 `update_topo` 的安全摘要，但仍只处理 Dock 网关自身的 `osd` 基础遥测，尚未据此解析子设备属性。
- EMQX、TLS、账号权限和真实测试机场的只读验证。

因此，当前代码只能为后续实时数据接收做准备，尚不能宣称 Dock 3 已完成上云或可连接真实设备。

## 六、现有代码的必改项

在真实连接前，需要按以下顺序修改：

1. **完成组织绑定能力**：将已登记的组织与设备资料接入 `airport_organization_get`、`airport_organization_bind`，并实现准确的 `requests_reply`；设备绑定码只能从受保护的服务器配置临时读取，不能写进数据库、网页、源码或日志；资料不完整时不得报告绑定成功。
2. **按官方报文解析数据**：MQTT 报文的业务字段位于 `data` 中，现有代码直接从根节点读取经纬度、电量和高度会得到错误数据；还需依据 `gateway_sn` 和拓扑区分机场、飞行器与 Pilot 数据。
3. **增加 Pilot 上云服务**：若要接入 Pilot 2，需要提供 H5 登录页、JSBridge 调用，以及向 H5 返回 MQTT 参数的 HTTPS 接口；这与 Dock 3 的 Broker 连接是配套但独立的流程。
4. **收紧部署安全性**：真实环境使用独立的 integration 配置，不默认启用 DJI 功能；EMQX 禁止匿名登录，配置账号权限和 TLS。真实 MQTT 就绪状态不能继续依赖 HTTP API 的就绪判断。
5. **保持控制关闭**：`services`、`property/set`、`drc/down` 等下行操作 Topic 继续禁用；第一阶段只实现必要的上云握手与只读数据接收。

## 七、安全边界

- App 凭证、设备绑定码、Broker 密码和浏览器会话令牌只保存在未纳入 Git 的受保护环境变量文件中；设备 SN 与组织资料只作为本机“待绑定”登记数据保存，不能据此推断已完成真实绑定。
- 在完成上述服务端应答、测试环境核验和明确授权前，不连接设备、不发布下行指令、不执行飞行操作。
