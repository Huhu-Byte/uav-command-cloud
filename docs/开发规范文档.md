## 写在前面：为什么要有规范？

做软件项目和做家务有点像。如果你一个人住，东西随便放也没关系，自己找得到就行。
但项目会越来越大，今天写的代码过两周你自己可能都忘了放哪了。

规范就是**给这个项目定一些规矩**，让所有人都知道东西该放哪、名字该怎么起。
这样以后加功能、修问题的时候，就不会手忙脚乱。

下面每一条都会先告诉你**为什么要这样做**，再告诉你**具体怎么做**。
看不懂的随时停下来问我。

## 一、项目结构 —— 文件夹怎么分

### 为什么要这样分？

写代码就像整理衣柜。你把 T 恤放在一个抽屉、裤子放另一个抽屉，想穿什么的时候就不用翻遍整个柜子。
项目里的代码也一样——不同种类的代码分开放，以后找东西好找得多。

### 具体怎么分

`
上云api私有化部署/
│
├── backend/              ← 后端代码
│     这里放的是服务器的程序，负责处理数据、和大疆的服务器通信等
│     用的技术叫 Spring Boot（一种 Java 框架，后面会讲）
│
├── frontend/             ← 前端代码

├── docs/                 ← 文档

## 二、Git —— 怎么"存档"代码

### Git 是什么？

Git 就像**游戏里的存档功能**。

你玩游戏的时候，每过一个关卡都会存一下档，这样万一后面打不过了，还能读档回到之前的地方。
Git 就是给代码做这件事的——每次你写完一段代码，就可以"存一次档"（这叫 **commit**，中文叫提交）。

存档的好处：
- 写错了可以回到之前正确的版本
- 可以清楚看到"上次改了哪里"
- 万一电脑坏了，代码也不会丢（如果存在 GitHub 上的话）

> 你的项目里已经有 Git 了，是一个**本地仓库**，目前有几次提交记录。

### 2.1 分支是什么？

分支可以理解为**平行世界**。
- master 分支（也叫主分支）是**稳定可用的版本**
- 如果你想加一个新功能，就创建一个新的分支（平行世界）来做
- 做好之后再把新分支**合并**回主分支

这样做的目的是：不会因为你在做新功能，而影响别人使用稳定的版本。

### 分支怎么命名

| 场景 | 分支名字示例 | 中文意思 |
|------|-------------|---------|
| 加一个新功能 | eature/航线规划 | 我在这条分支上加"航线规划"这个功能 |
| 修一个 bug | ix/地图加载失败 | 我在这条分支上修"地图加载失败"这个问题 |
| 做一些小调整 | chore/更新依赖 | 更新一下用到的工具包之类的杂活 |

### 2.2 Commit 怎么写（每次"存档"时写一句话）

每次提交的时候，要写一句话说明这次做了什么。
格式很简单：

`
[类型] 你做了什么
`

几个常见的类型：

| 类型 | 什么时候用 | 例子 |
|------|-----------|------|
| feat | 加了一个新功能 | [feat] 添加无人机状态显示 |
| fix | 修了一个问题 | [fix] 修复地图加载失败 |
| docs | 改了文档 | [docs] 更新配置文件说明 |
| chore | 杂活（更新依赖、整理文件等） | [chore] 更新 Spring Boot 版本 |

> 千万不要写"修改了一些东西"——这话说了等于没说。**要写清楚你到底改了啥。**

### 2.3 什么时候提交（什么时候"存档"）

- 写了一个小功能，确认它跑得起来了 → **就提交**
- 不要攒了几百行代码才提一次交——那样万一出错，你都不知道哪里出的问题

> 简单来说：做一点，存一次。

> **2026-07-31 增补**：以上是基本规则。还有更严格的"保存铁律"，看[第十节](#十血的教训--保存铁律2026-07-31-增补)——那是用一天的工作成果换来的教训。

## 三、代码风格 —— 名字怎么起、格式怎么写

### 为什么要统一代码风格？

就像写作文有标点符号规范一样，代码也有一些约定俗成的规矩。
这样做的好处是：你写的代码别人能看懂，别人写的代码你也看得懂。

### 如果是写 Java 后端

| 规矩 | 例子 | 说明 |
|------|------|------|
| 类名：每个单词首字母大写 | DroneController | 这叫**大驼峰**，因为驼峰是凸起的，首字母大写就像驼峰最高点 |
| 方法名/变量名：第一个单词全小写，后面每个单词首字母大写 | getFlightPath()、droneStatus | 这叫**小驼峰** |
| 缩进：用 4 个空格 | | 相当于每按一次 Tab（但最好设置编辑器自动转成空格） |
| 注释：写清楚这段代码是干什么的 | // 计算无人机到目标点的距离 | 不要写废话，比如 // 设置一个变量 这种 |

### 如果是写 Vue 前端

| 规矩 | 例子 |
|------|------|
| 组件文件（一个页面或一个功能块）：大驼峰 | FlightMap.vue、DroneStatus.vue |
| 变量和函数：小驼峰 | droneList、getFlightData() |
| 写法：用<script setup>这种新写法 | 这个先记着，写到的时候我教你 |

### 如果是写 Python AI 服务

| 规矩 | 例子 |
|------|------|
| 文件名：全小写，单词之间用下划线 | detect_objects.py |
| 函数名和变量名：全小写，单词之间用下划线 | detect_objects()、confidence_score |
| 缩进：4 个空格 | Python 对缩进特别敏感，一定要对齐 |

## 四、API 接口约定 —— 前后端怎么"说话"

### API 是什么？

简单理解：API 就是两个程序之间约定好的"对话方式"。

你的前端（网页）和后端（服务器）需要互相传数据，它们怎么传、用什么格式，需要提前商量好。
就像你点外卖——你报地址和手机号，老板确认订单，这个流程是固定的。

### 我们的约定

**第一，所有返回的数据都用同样的格式：**

`json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
`

- code: 0 说明一切正常
- code 不是 0 说明出错了，比如 code: 40001 表示"参数错误"
- message 是给人看的提示信息
- data 是实际要传的数据，成功了就放数据，失败了就放空

**第二，接口地址前面统一加 /api/v1/**

比如：
- 获取无人机列表：/api/v1/drones
- 创建任务：/api/v1/tasks

1 表示版本 1，以后升级了就改成 2，这样旧的接口还能用。

## 五、数据库约定 —— 数据怎么存

### 数据库是用来干什么的？

简单说，数据库就是**一个专门存数据的地方**。
用户信息、无人机状态、飞行记录……这些都存在数据库里。

### 我们的约定

**表名（可以理解为一张表格的名字）：**
- 全小写，单词之间用下划线
- 比如：uav_flight_record（无人机飞行记录）

**每张表都有的统一字段：**

| 字段名 | 意思 | 说明 |
|--------|------|------|
| id | 编号 | 每一条数据唯一的编号，自动递增 |
| created_at | 创建时间 | 这条数据是什么时候创建的 |
| updated_at | 更新时间 | 这条数据最近一次修改的时间 |
| deleted_at | 删除时间 | 默认是 0。如果删除了就记录删除时间（这叫"软删除"，数据还在但用不了，方便恢复） |

## 六、配置文件 —— 不同环境用不同设置

### 什么叫"环境"？

你在自己电脑上写代码叫**开发环境**，
测试人员检查代码有没有问题叫**测试环境**，
用户使用的叫**正式环境**（或者叫生产环境）。

不同环境需要的配置不一样——比如你在本地连的数据库和正式环境用的数据库肯定不是同一个。

### 怎么管理

我们准备三套配置：

| 环境 | 配置文件名 | 什么时候用 |
|------|-----------|-----------|
| 本地开发 | pplication-dev.yml | 你自己电脑上跑的时候 |
| 测试 | pplication-staging.yml | 部署到测试服务器的时候 |
| 正式部署 | pplication-prod.yml | 用户真正用的时候 |

**重要的提醒：** 数据库密码、API Key 这些东西**绝对不能直接写在代码里**。
要用环境变量（简单理解就是不想写死在代码里的秘密信息）。
后面部署的时候我会教你怎么做。

## 九、工作日志 —— 每次改了什么都要写下来

### 为什么要有工作日志？

2026-07-31 发生了一次严重事故：AI 助手在清理后端源码时，未经 git 提交就删除了 57 个 DJI 集成文件，导致一天的工作成果全部丢失，只能靠项目记忆重新搭建。

教训：**代码可以重建，但前提是你要知道丢了什么。** 工作日志就是那道保险——它让你随时能说出"今天做了哪些改动、改了哪些文件、验证结果是什么"。

### 日志放哪

项目根目录的 `工作日志.md`。和 `.project-memory.md`、`AGENTS.md` 同级，第一眼就能看到。

### 怎么写

每条记录固定四个部分：

`
## 日期

### 标题（简短描述做了什么）

**目的**：为什么要做这个改动
**改动文件**：列出所有修改/新建的文件
**完成内容**：实际做了什么
**验证结果**：`mvn test` 通过？`npm run build` 通过？浏览器确认过了？
`

对应关系：**每个 git commit 都应该对应日志里的一条记录。** 看 git log 能找到日志条目，反之亦然。

## 十、血的教训 —— 保存铁律（2026-07-31 增补）

### 第一条：改之前先存档

**任何涉及以下操作的动作，必须先 `git add -A && git commit`：**

- 删除文件（哪怕只是一个）
- 批量覆盖或同步目录
- 运行自动清理脚本
- 跨项目复制粘贴代码

不允许在 dirty 工作区上做破坏性操作。如果当时的工作还没到可提交的程度，至少用 `git stash` 暂存。

### 第二条：小步提交，不攒一堆

- 写完一个类、跑通一个测试 —— **就提交**
- 不要等"今天把所有功能写完再一起交"
- 攒了几十个文件的提交，一旦写错连回滚都找不到从哪开始

### 第三条：新功能必须走分支

- **永远不在 master 上直接开发新功能。**
- 新功能 → `feature/功能名` 分支
- 修 bug → `fix/问题描述` 分支
- 做完、测试通过 → 合并回 master

当前 DJI 集成已经误上了 master，这是例外。后续所有新功能严格走分支。

### 第四条：日志和代码同生共死

- 改代码的同时更新 `工作日志.md`
- 日志写完立刻和代码一起提交
- 不要"先改代码、回头再补日志"——一定会忘
